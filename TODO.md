## Tier 2 — meaningfully improves what's there

- **Eval / quality measurement.** A smoke-test set of ~20 (question → expected_entity) pairs to measure retrieval recall@k. Doesn't matter if retrieval is good if you can't measure it. Free, small effort, naturally paired with the chatbot build.
- **README rewrite.** Currently describes only the OCR foundation. Should reflect the full pipeline — pass 1, dedup, merge, sweep, heuristic, canonicalize, pass 2 (windowed + local registry), per-doc-section format, cost tracking, orchestrator usage. Free, ~30 min, reduces re-onboarding cost the next time you pick this up.
- **Pre-pass-1 canonical-name verification at ingest time.** [verify_canonical_names.py](verify_canonical_names.py) exists but only runs on demand. Wire into the orchestrator so canonical-name typos surface during ingest, not after pass 2 has propagated them everywhere. Cheap (~$0.05 per ingest).
- **Code cleanup before adding new features.** Audit existing modules for dead code or scripts no longer used. Bundle related scripts into folders (e.g., `pipeline/` for orchestrator stages, `tools/` for one-off helpers like `verify_canonical_names`, `dedup_registry`). Reduces friction for the chatbot work.
- **Page-edit cascade tool.** Use the citation graph to surgically update entities when source content changes. Each entity already has `source_pages: {doc_tag: [page_numbers]}` in frontmatter and `(p. N)` citations in relationship bullets — given `(doc_tag, edited_pages)` as input, the tool walks `graph/entities/`, finds entities whose `source_pages[doc_tag]` intersects the edited set, removes the relevant relationship bullets and `## Source: <tag>` sections, and updates frontmatter. Then a normal `--start-from registry --doc-tag X` re-run regenerates only the invalidated entities (pass-2 `skip_existing=True` skips the untouched ones). Cleaner than re-pass-2-ing the whole doc for a single-page fix; cost drops from $3-5/doc to $0.10-0.50 for a typical OCR correction. Most useful once there's a frontend for typo reporting (Tier 4) — until then, manual edits to combined.md → run cascade → re-run pipeline. ~80 lines.
- **Pass-2 contextual disambiguation of common-word aliases.** Aliases like `demons` (for tanar'ri), `the Cage` (for Sigil), `Prime` (for Prime Material Plane) cause false positives in pass-2 windowing — paragraphs containing the alias in unrelated/metaphorical use ("her inner demons") get pulled into the entity's window and may produce spurious relationships. Proposal: between window-building and pass-2 submission, run a small Haiku batched filter per entity that has at least one "risky" alias (single-word lowercase, or all-common-stopwords). Filter only the paragraphs that matched ONLY via a risky alias (canonical or specific-alias matches skip filtering). The filter judges each paragraph: "does this refer to <entity> in its D&D-Planescape sense?" Estimated overhead ~$0.05-0.15 per doc — basically free. Real quality win on adventure modules where generic-noun overlap is heaviest.
- **Populate `books` arrays in `chatbot/doc_sources.json` for boxed sets.** The schema supports per-book page-range mapping inside multi-book products (e.g. TSR 2600 contains *A Player's Guide*, *A DM Guide*, *Sigil and Beyond*, *Monstrous Supplement*). Without it, citations show "(campaign_setting, p. 110)" — meaningless to someone holding the physical books. With it, the chatbot displays "(Sigil and Beyond, p. 14)". Each box is ~5 minutes of flipping the PDF to find book boundaries. Worth doing for: campaign_setting, planes_of_chaos, planes_of_law, planes_of_conflict, hellbound. Single-book products don't need it.

## Tier 3 — quality polishes

- **Cross-document profile synthesis.** Per-doc-section format preserves provenance but doesn't synthesize across sources. A future LLM step could read all `## Source: X` sections and produce a unified description while keeping the per-doc evidence as appendices. Defer until current per-doc output proves insufficient (it might be fine for retrieval). Costs ~$10–15/doc to redo.
- **Heuristic candidate extractor improvements** ([heuristic_entity_candidates.py](heuristic_entity_candidates.py)) — currently word-boundary regex misses lowercase-only D&D names like `tanar'ri`, `baatezu`, `slaad`. A separate "known-creature-name patterns" pass could pick these up. Modest quality gain, cheap.
- **Better cache investigation.** Anthropic batches charged cache_write ~N times instead of 1× write + (N−1)× reads on the original PoL batch. Sidestepped by local registry; remains an open question. Mostly intellectual curiosity at this point.
- **Per-doc OCR corrections in corpus profile.** Currently `### OCR corrections` in the profile is a global find-and-replace — applied to every doc using that profile. Adding `kytonia → yugoloths` globally would mangle real `kytonia` mentions in any other doc. Proposal: support `### OCR corrections (doc:<tag>)` subsections in the profile parser, and have stages 2/5/6/8 apply global + matching doc-tagged corrections. ~50 lines: extend `parse_ocr_corrections()` to accept a `doc_tag` arg, plumb it through. Lets every doc have its own quirk-list without poisoning others. (For now, single-occurrence fixes are made by editing `ocr/<doc_tag>.md` directly — the page-edit cascade tool covers the propagation.)
- **Pass-2 frontmatter refresh for skip_existing entities.** Pass-2 writes each entity .md ONCE during the first doc that profiles it, then `skip_existing=True` skips later docs. So aliases / supertypes / source_documents that grow in the registry from later docs' merge/sweep/heuristic stages don't propagate to existing entity files. Workaround: `tools/refresh_entity_frontmatter.py` re-stamps frontmatter from current registry — must be run manually after each batch. Better fix: at pass-2 collect time, for entities being skipped, *still* call `_build_frontmatter` with the latest registry data and rewrite just the frontmatter block (preserve body). No LLM cost added. ~30 lines in `extract_profiles.py`.
- **Cross-doc pass-2 backfill for the original 4 docs.** Campaign setting, Planes of Chaos, Planes of Law, and Player's Primer were ingested before the two-phase architecture. Their entity files were written with whatever registry state existed at that moment — they don't have wikilinks to entities introduced by later docs. `python -m planescapeRAG.run_pipeline --doc-tag X --start-from profiles_submit --pass2-no-skip-existing` for each of those four would regenerate them against the now-complete registry. Cost: ~$15-25 across the four. Not blocking — retrieval probably still works on the 1-hop graph traversal — but the early docs' entity bodies are mildly stale.
- **Switch sweep model to Haiku.** Sweep is ~$1-1.50/call with Sonnet (now the dominant marginal cost per ingest after pass-2 was optimized). The sweep prompt is "find missing entities given doc + slim registry" — easier reasoning than pass-2's "profile this entity with relationships". Haiku 4.5 likely handles it 80%+ as well at 3× cheaper. Add a `--sweep-model` flag to `run_pipeline.py` defaulting to current behavior; spot-check on one doc; if quality holds, flip the default. Saves ~$15-25 across a 23-doc batch.

## Tier 4 — out of scope until prerequisites exist

- **Frontend typo reporting UI** — let users flag canonical names or quoted text in the rendered graph that look wrong. Capture `(entity, span, suggested correction)`. Pipe into the corpus profile's `### OCR corrections` section as new `old → new` bullets. The mechanism for applying corrections is already built ([ocr.py](ocr.py) `apply_ocr_corrections`); the gap is the reporting + persistence flow. **Needs a frontend to exist first.**
- **Graph DB importer.** When ready to migrate from markdown-as-graph to a real graph DB, a one-shot importer can walk `graph/entities/`, parse each file's frontmatter and Relationships bullets, and emit Cypher (Neo4j) or equivalent. Keep canonical-name consistency so the importer is trivial. **Wait until there's a reason to migrate.**
- **Confluence-scale architecture sketch.** Local-registry approach already adopted is a prerequisite. Beyond that: page-level change detection, per-page entity diffing, permissions-aware retrieval. **Speculative; revisit if/when there's an actual second corpus.**
- **Make the OCR step optional.** For Confluence/HTML/structured sources, skip the OCR pipeline entirely. Generic interface: any source ingestion produces a `combined.md` that downstream stages consume. **Coupled with Confluence-scale concern.**
- **Public-sharing hardening.** If the chatbot UI is ever exposed publicly (Cloudflare Tunnel, Tailscale Funnel, deployed instance), the cost surface becomes real — anonymous users can drain Anthropic spend via `/chat`. Concrete asks, gated behind a `PLANESCAPE_PUBLIC=1` env var so local dev is unaffected: (1) `slowapi` rate limit on `/chat` and `/query`, ~10/min/IP; (2) shared-secret token check (`?token=…` query param) refused at middleware; (3) daily cost cap reading `cost.session_total()`, refuse new requests above $X; (4) `FastAPI(docs_url=None, redoc_url=None)` to hide the API surface from scanners; (5) `max_length=2000` on the `question` field; (6) hard refusal of Sonnet/Opus selection from public requests (Haiku-only). Also: never set `PLANESCAPE_SHOW_PAGES=1` in any public deployment — the page-image endpoint exposes scanned TSR/WoTC pages and is a copyright takedown waiting to happen. **Wait until there's an actual reason to share publicly (e.g., persistent demo URL on a portfolio).**
